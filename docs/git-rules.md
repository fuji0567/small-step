# Git ルール

このリポジトリの Git 運用の正本です。作業規則の全体は [AGENTS.md](../AGENTS.md) を参照します。

## ブランチ戦略（git-flow）

git-flow に従います。

| ブランチ | 役割 | 分岐元 | 統合先 |
| --- | --- | --- | --- |
| `main` | 公開・リリース済みの状態。直接コミットしない | - | - |
| `develop` | 次のリリースに向けた統合ブランチ | `main` | `main`（リリース時） |
| `feature/<内容>` | 機能・Phase 単位の開発 | `develop` | `develop` |
| `release/<版>` | リリース準備（版の確定、軽微な修正のみ） | `develop` | `main` と `develop` |
| `hotfix/<内容>` | `main` の緊急修正 | `main` | `main` と `develop` |

- 既定ブランチは `main`、日常の統合先は `develop`。
- 大きな Phase は目的別に `feature/` を分け、既存 Phase の修正を次の Phase に混ぜない。独立した Phase は必要な時点の `develop` から分岐してよい。
- 統合は `git merge --no-ff <ブランチ名>` を使い、統合したブランチは削除する。
- 作業を始める前に作業ツリーを確認し、既存の未コミット変更を保持する。

## 命名規則

### ブランチ

- 形式は `<種別>/<短い内容>`。種別は `feature` / `release` / `hotfix`。
- 内容は英小文字・数字・ハイフンの短い英語にする。Phase の作業は番号を付ける（例: `feature/phase3-lut-preview`）。
- `release/` は版を使う（例: `release/0.2.0`）。

### コミットメッセージ

- 形式は `<種類>: <要約>`。要約は日本語または英語で、1行にまとめる。
- 種類は次のいずれか。

| 種類 | 使う場面 |
| --- | --- |
| `feat` | 機能の追加 |
| `fix` | 不具合の修正 |
| `docs` | 文書のみの変更 |
| `refactor` | 動作を変えない整理 |
| `chore` | ビルド・設定・依存などの雑務 |

- 確認が通ってから1目的1コミットにする。仕様変更は担当仕様書と同じコミットに含める。

## マージとレビュー

- マージはユーザーのレビューが終わってから行う。レビュー前に `develop` / `main` へマージしない。
- 統合前に差分と検証結果をユーザーへ示す。
- リモートへの push、`main` へのマージはそれぞれ対象を明示し、ユーザーの承認を得てから行う。
- リモートの変更と push はユーザーに頼まれたときだけ行う。

## 作成者の表記

- Claude などの AI エージェントは、Git の履歴に自分の名前を出さない。
- コミットメッセージに `Co-Authored-By` などの共著表記や生成元の署名を付けない。
- PR の説明文にも生成元の表記を付けない。

## コミットしないもの

写真原本、私的な CR2 / JPEG、Wi-Fi 認証情報、API キー、署名鍵、ビルド生成物はコミットしません。テスト素材は再配布条件が明確なものだけを使います。

## 禁止と注意

- `push --force`、`reset --hard`、履歴の書き換えはユーザーに頼まれたときだけ行う。
- `git` が dubious ownership を返す場合は、この作業ツリーと所有者を確認したうえで `git -c safe.directory=<確認済みの作業ツリーの絶対パス> ...` を使う。グローバルの安全設定を広げない。
- `safe.directory` にはこのリポジトリの確認済みパスを指定する。他プロジェクトのパスをそのまま使わない。
